浏览器的请求本身是异步并行的，浏览器可以同时发起多个请求，不会因为一个请求的慢而阻塞其他请求。但是在 HTTP/1.1 协议下，即便浏览器可以发起并行请求，**HTTP队头阻塞**的问题仍然会出现，原因在于 HTTP/1.1 协议是基于 **请求/响应** 模型的，并且每个请求和响应都需要通过同一个连接来传输。

### 为什么 HTTP/1.1 中会出现队头阻塞？

1. **HTTP/1.1 连接复用**：在 HTTP/1.1 中，如果浏览器和服务器之间已经建立了连接，多个请求会通过同一个连接复用。但是，这个连接是 **串行的**，即请求和响应必须按顺序来。也就是说，尽管浏览器可以并行发起多个请求，但它们的响应却必须按请求的顺序接收。

2. **队头阻塞的发生**：假设客户端发起了多个请求，且请求 A 的响应非常慢，如果该请求先返回，那么请求 B 和请求 C 必须等待 A 的响应完成后才能继续返回，即便它们早已准备好响应。这就是 **队头阻塞**，因为响应的顺序无法跳过或者重排，必须按请求顺序处理。

   - **例子**：假设客户端同时发起三个请求：
     - 请求 A：大型图片，需要长时间处理。
     - 请求 B：小的 CSS 文件，响应已准备好。
     - 请求 C：小的 JS 文件，响应也已准备好。

   在 HTTP/1.1 中，响应的顺序是严格按照请求的顺序来返回的。所以，即使请求 B 和请求 C 已经准备好返回，仍然要等请求 A 完成后，B 和 C 才能返回。这就造成了 **队头阻塞**。

### 为什么在 HTTP/2 中解决了队头阻塞？

在 HTTP/2 中，**多路复用**（multiplexing）是解决队头阻塞的关键特性。通过多路复用，多个请求和响应可以在同一个连接上并行传输，响应的顺序不再受请求的顺序影响。

- **多路复用**：即多个请求和响应可以并行发送和接收。即便请求 A 比请求 B 慢，其他请求的响应可以提前完成并返回给客户端，而不会因为 A 请求慢而阻塞 B 和 C 的响应。
- **流和优先级**：HTTP/2 还允许请求/响应分配不同的优先级和流，这样可以更加精确地控制请求的发送和响应的接收，进一步减少了阻塞的风险。

### 小结

- **HTTP队头阻塞** 是因为 HTTP/1.1 中使用的是串行的请求/响应模型，而不是并行模型。即便浏览器能并行发送多个请求，但是服务器必须按顺序返回响应，导致某个请求的慢响应会阻塞其他请求。
- **HTTP/2 的多路复用** 改进了这一点，使得多个请求和响应可以并行传输，不会再受请求的顺序影响，从而有效避免了队头阻塞。

所以，队头阻塞并不是浏览器的请求发起方式（异步并行）的问题，而是 **协议层面** 的限制。
